# Model distribution and version updates

`models/registry.json` uses schema version 2. A stable `id` identifies the model family; `latestVersion` selects the currently offered version; each `versions[]` entry contains a checkpoint version, format, optional version-specific class mapping (otherwise it inherits the model's classes), exact filename, byte size, SHA-256, and optional URL/development source. Do not reuse a version string for different bytes or metadata. A behavior-changing checkpoint is a new model version and remains an explicit user choice in Model Manager.

Both checkpoint files are published in the public [`models-v1` GitHub Release](https://github.com/SamirShaikh05/Boundary-Vision/releases/tag/models-v1), and the registry links directly to those assets. No newer model version or checksum has been invented.

The published release assets report these same byte sizes and SHA-256 digests. This verifies the hosted files' release metadata against the registry and local checkpoints; it does not establish a successful Model Manager download, runtime load, or inference test. The public registry is served from [`models/registry.json` on `main`](https://raw.githubusercontent.com/SamirShaikh05/Boundary-Vision/main/models/registry.json). The public copy still contains legacy `minimumPython` metadata, which this application ignores; the local registry no longer declares a Python version threshold. The public registry will remain unchanged until a separate registry publication is authorized.

The base installer contains only this registry, never a `.pt` checkpoint. The repository can be cloned without model weights: the two `.pt` files are distributed by the `models-v1` release and ignored by Git. To use a checkpoint from a development checkout, download the matching asset from that Release into `models/` under its registry filename. Verify its expected size and SHA-256 from `models/registry.json` before relying on it. The source app can instead install hosted weights through Model Manager; when a valid local development file exists, the manager may use it as its install source. Missing local files do not prevent the app from starting or the registry from offering the hosted download.

The Windows installer build reads the checked-in registry and never bundles model weights. A local checkpoint is optional; if present, the packaging script checks its size and SHA-256, and if absent the script proceeds without downloading it. The Model Manager uses storage at `userData/models/{id}/{version}/{filename}`. It also reads the previous unversioned managed path for migration compatibility without moving or deleting it. The selected model ID and version remain in user settings across app updates.

At startup and at most every 15 minutes, Model Manager fetches the authoritative registry from `https://raw.githubusercontent.com/SamirShaikh05/Boundary-Vision/main/models/registry.json`. It validates schema, IDs, version metadata, HTTPS asset URLs, file sizes and hashes before using it. If the remote registry is unavailable or invalid, it falls back to the registry bundled with the app so local inference remains available. A newer registry version is shown as an update only when a different installed version exists and the latest checkpoint has a usable download source.

## Adding a hosted model version

1. Publish an immutable checkpoint object to a controlled, public HTTPS origin. A version update uses a new version identifier and a new object key; never replace bytes at a previously published key.
2. Independently download the final served object and calculate its byte size and SHA-256. Have the model owner provide accurate behavior/change notes for the new version; do not derive or guess these values.
3. Add a new `versions[]` item under the existing stable model ID. Set `format` to a runtime-supported value (`ultralytics-yolo` is currently supported), the exact checksums, accurate `changeSummary`, and a `downloadUrl` only after hosting is active. Set `latestVersion` to the intended offered version. Keep prior version records so users can continue selecting or removing old installed versions.
4. The package script checks a development checkpoint against its declared size/hash if the file exists, removes development-source paths from the app registry, and generates URLs for configured versions from `BOUNDARY_VISION_MODEL_BASE_URL` using `/models/{id}/{version}/{filename}`. Missing local weights are not downloaded during packaging. It does not upload checkpoint assets. Independently verify the resulting registry and public object after building.

`models/hosting.example.json` remains an unconfigured template for a separate static HTTPS host. It is not the source of the currently published files: the current registry uses immutable GitHub Release asset URLs. No credentials are needed for those public downloads. The assets are published, but end-to-end downloads and inference have not yet been verified in the packaged app.

Model asset distribution and application release publishing are separate workflows. `models-v1` hosts model checkpoint files; an application release uses the separate electron-builder GitHub publishing configuration and its own versioned installer/update metadata. `npm run package:win` only builds locally, while `npm run release:win` is the publishing path and requires release credentials/signing configuration. Neither command uploads model weights.

## Installation and activation safety

The user explicitly starts each installation and separately chooses which installed version to use for inference. A download goes to a temporary file under that version's managed directory. The manager checks HTTPS through at most five redirects, caps bytes at the declared size, checks exact final size and SHA-256, then invokes the bundled Python worker to load the staged `.pt` file and verify the registered class order. Only after those checks does it rename the staged file to its versioned destination. Existing versions are kept; installing a new version does not select it or remove an older version. Selection validates the version again before saving `selectedModelId` and `selectedModelVersion`.

Model install/validation is blocked while inference is running; inference cannot start during model installation/validation. Removal is version-specific and refuses the selected version or a version currently used by inference. The registry rejects unsupported model formats. Model compatibility is established by the actual worker: dependencies must import, the checkpoint must load and match the registered classes, and inference must run. Errors from those operations are reported at the point of use; no registry Python-version threshold is treated as proof of compatibility. The packaged worker uses its own bundled Python runtime. Development and packaging use the pinned environment in `.python-version` for reproducibility. If URLs remain unset, the UI says the model source is not configured and no download is attempted.
