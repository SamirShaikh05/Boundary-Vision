# Application update releases

Boundary Vision uses `electron-updater` with the electron-builder GitHub Releases provider and the Windows x64 NSIS target. The release repository is intentionally not named in this source tree because no GitHub repository was provided. `electron-builder.config.cjs` reads `BOUNDARY_VISION_GITHUB_OWNER` and `BOUNDARY_VISION_GITHUB_REPO`; it rejects a partial/invalid pair and configures a draft GitHub release when both are supplied. electron-builder embeds the update feed as `resources/app-update.yml` and creates `latest.yml` plus the NSIS installer and blockmap assets. No token or repository URL is hard-coded.

The app checks at startup and from **Settings & About → Check for updates** only when it is packaged with that feed metadata. Development builds report that updates are disabled. Updates are never downloaded automatically: the user selects Download, then Restart to install. The updater does not install on ordinary app quit. The main process rejects a restart while inference or a model update is active. A downloaded update can wait until the user returns. Offline or missing-release errors are shown with a retry action. electron-updater checks the release version and platform/architecture; Windows update signature validation depends on using the same trusted signing identity for the installed app and its updates.

## Build and publish a Windows release

1. Create/use the actual **public** GitHub repository and configure the repository secrets/access for the release owner. Do not ship a GitHub token in the app. A private release repository would require end-user credentials and is not configured here.
2. Update the app version in `frontend/package.json` and `frontend/package-lock.json`; use a strictly increasing release version. Update app/model compatibility or release notes as appropriate. Run `npm ci` and `npm run build` first.
3. Configure the real owner and repository in the release shell, plus a narrowly scoped `GH_TOKEN` that can create/upload releases. Configure the Windows signing certificate using electron-builder's supported secure environment variables (for example `CSC_LINK` or `WIN_CSC_LINK` and, if needed, `CSC_KEY_PASSWORD`). Do not place token or private-key material in source, checked-in config, or logs.
4. On the Windows x64 release machine with the required Python environment and reviewed FFmpeg build, prepare the complete corresponding-source and third-party source archive for that exact GPL FFmpeg build. Set `BOUNDARY_VISION_FFMPEG_SOURCE_ARCHIVE` to the archive file, then run `npm run release:win`. The script checks that the supplied FFmpeg matches the reviewed Gyan 9.0.2 GPLv3 profile and refuses publishing if the source archive path is absent. The archive is not uploaded automatically; add it to the GitHub draft release and provide its source access with the release before publishing.
5. Verify the draft's installer, `.blockmap`, `latest.yml`, and corresponding-source archive; verify Authenticode signatures on the installer, Electron app, worker, FFmpeg and FFprobe; verify the generated `resources/app-update.yml` points to the intended repository; install this exact signed build and test update check/download/restart against a later test release. Publish the draft only after those checks, then verify the public assets and update again from a clean install.
6. Publish a signed update-enabled bootstrap installer manually for users on any older build that lacks `app-update.yml`. Such an existing installation cannot discover the GitHub feed until it is replaced with an update-enabled build.

The current app version remains `0.1.0`, the GitHub owner/repository is unset, and no signing identity, GitHub token, or corresponding-source bundle is configured in this repository. Therefore `npm run package:win` creates an offline/local installer with update checking disabled. `npm run release:win` is configured but refuses to proceed until the owner supplies those external values and `BOUNDARY_VISION_FFMPEG_SOURCE_ARCHIVE` points to a reviewed bundle; the source bundle must also be manually attached to the draft release. Live checking, downloading, signature validation on a real signing certificate, and restart/install have not been exercised against a published release. The audited local rebuild is not a live-update build because `resources/app-update.yml` is absent.

See the official [electron-builder auto-update guide](https://www.electron.build/v26/docs/features/auto-update/), [GitHub publishing guide](https://www.electron.build/v26/docs/publish/), and [electron-updater API](https://www.electron.build/v26/docs/api/electron-updater.class.appupdater/).
